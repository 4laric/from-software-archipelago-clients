# Agent and contributor rules

Read [CONTRIBUTING.md](CONTRIBUTING.md) first. This file holds the rules that
are easy to break without noticing.

## Client updates must keep old seeds working

Players are mid-run on seeds generated by an earlier apworld and launcher
release, and the standard upgrade path for them is to replace **only** the
client binary. A client change is therefore backwards compatible with every
seed the previous release accepted unless it is loudly flagged as not.

"Compatible" covers all of these at once:

- **Seed contract.** Slot data, `runtime_config.json`, and the runtime build
  string an older world emits still load. New fields are optional with a
  default; removed fields are tolerated, not refused.
- **Persisted state.** Existing ledgers, receipts, journals, parks, and
  watermarks parse and keep their meaning. No schema-version bump without a
  migration that runs on load.
- **Recovery.** If a newer rule has to refuse something an older client
  persisted, refuse it by *parking that one item* through the existing
  terminal-failure path so the stream advances, name the index in the
  diagnostic, and make sure an existing console command (`blocked`,
  `retry INDEX CONFIRM`, `reissue`) clears it. A bare error that re-raises on
  every poll is a stall, not a refusal. Worked example: the reinforced-shield
  park in `crates/bb-archipelago/src/client_loop.rs` (PR #641), which
  replaced a bail that had wedged every later item.
- **Launcher interface.** CLI flags and config keys the launcher writes keep
  working; new ones are optional.
- **Behavior parity.** If delivery outcomes change for an existing run (for
  example an upgrade-level census now sees more weapons), say so in the
  changelog even when nothing breaks.

## When breaking compatibility is the right call

Sometimes it is. Then it must be loud, in all of these places:

1. Bump the cross-repo runtime build string (`RUNTIME_BUILD` in
   `crates/bb-archipelago/src/lib.rs`) together with the apworld's copy, so
   the client refuses old seeds up front with a clear message instead of
   misbehaving later.
2. Put a **Breaking** section at the top of the crate changelog that says
   what stops working and what players mid-run should do.
3. Title the pull request with the break and reference the release it lands
   in. A release that carries a break is a major (or, pre-1.0, a minor)
   version bump, never a patch.

If you are not sure whether a change is breaking, treat it as breaking and
ask in the pull request before merging.

## Checks to run before opening a client PR

- `cargo fmt -- --check` (CI fails on formatting alone, with `-Dwarnings`).
- `cargo test -p bb-archipelago --lib -- --test-threads=1` for Bloodborne;
  one logging test is flaky under parallel execution.
- Add or update a test that loads state written by the previous release's
  shape whenever you touch persistence.
